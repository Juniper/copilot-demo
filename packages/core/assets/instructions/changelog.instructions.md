# Instructions for Updating the Changelog

- Make entries in the `CHANGELOG.md` file located at the root of the project workspace

- Use the format `## [Version] - YYYY-MM-DD` for each version entry, where `[Version]` is the version number and `YYYY-MM-DD` is the date of the change.

- Begin with the most recent version at the top of the changelog. 
 - Begin with the most recent version at the top of the changelog.
 - Maintain reverse chronological order: list the newest changes first (at the top of the file) and older changes below. When adding, editing, or merging entries, preserve this order so the top of the file always shows the most recent changes.

- Use clear, descriptive language to explain the changes made.

- Include the date of the change and the author(s) involved.

- Categorize changes into sections (e.g., Added, Changed, Deprecated, Removed, Fixed, Security) for better readability.

- Use bullet points for individual changes to enhance clarity.

- Reference any related issues or pull requests for context.

- **DO NOT** include code in the changelog, only contain descriptions of changes.

- Keep the changelog up to date with:
    - Every task completed
    - Every feature added
    - Every bug fixed
    - Performance improvements
    - Documentation updates

- Prioritize readability and clarity:
    - Use simple language
    - Avoid jargon
    - Ensure that anyone reading the changelog can understand the changes without needing to refer to the code

- If applicable, include links to relevant documentation or resources that provide additional context for the changes.

- Follow semantic versioning guidelines.
